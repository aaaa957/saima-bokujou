## 一、T5：`routeArcState` 的「热记忆」（免 WeakMap）—— 快 3.2%

第五轮之后的 profile：`routeArcState` inclusive **25.98%**（self 16.74%），仍是 #1。

它在每 300 步里被调用 **519 万次**、其中 252 万次未命中，而每次调用都要：

1. `ROUTE_STATE_VALUE_CACHE.get(geo)` —— 一次 **WeakMap** 查询
2. 未命中时还走 `loopArcTable(loop)` —— **再一次 WeakMap**（`has` + `get`）

但**一场比赛里 `geo` 与 `route.loop` 始终是同一个对象** ⇒ 这些查询纯属浪费。

**实现**：加一条 1 项记忆（`RS_GEO`/`RS_TABLE`），只在 `geo` 变化时才查表。

```
r₁ = 0.9686   r₂ = 1.0341   m = 1.0008（≈1，非常干净）
⭐ 效果 = 0.9678 ⇒ 快 3.2%
```

## 三、T7：定长「直接映射」记忆表取代 Map —— 快 12.9%

T5 之后 `routeArcState` 的剩余成本里，最大的一块是那个 **per-geo 的 `Map`**：

- 每 300 步 **519 万次** `has` + `get`（double 键要算哈希再查桶）
- 每次未命中一次 `set`
- 表满 4096 就**整表 `clear`** —— 每 300 步约 **615 次**

**实现**：改为定长直接映射表（8192 槽）

```js
const RS_KEY=new Float64Array(RS_SIZE),RS_VAL=new Array(RS_SIZE);
const RS_HBUF=new Float64Array(1),RS_HBITS=new Uint32Array(RS_HBUF.buffer);
...
RS_HBUF[0]=s;
const slot=(RS_HBITS[0]^Math.imul(RS_HBITS[1],0x9E3779B1))&RS_MASK;
if(RS_KEY[slot]===s)return RS_VAL[slot];
```

- 命中判据是 **`s` 逐位相等于键** —— 在有限值上与 `Map`(SameValueZero) 等价
- **无哈希桶、无扩容、无 `clear`**；未命中即重算并覆盖该槽（与「满则清空」同为记忆化）
- **换 `geo`（换一场比赛）时整表失效**（把键填成 NaN）⇒ 既避免跨 geo 命中，
  也避免跨比赛保留引用（原 WeakMap 无此问题，必须显式处理）
- 纯记忆化：**不改变任何数值**

```
r₁ = 0.8496   r₂ = 1.1205   m = 0.9757
⭐ 效果 = 0.8708 ⇒ 快 12.9%
```

> ⚠️ 同一次测量的 **CPU 口径只读出 3.4%**，与墙钟的 12.9% 不一致。
> 用**累计测量**交叉验证：逐项预测 `0.7853×0.9678×0.8708 = 0.6618`，
> 累计实测 **0.6762**（差 2.2%，噪声内）⇒ **T7 ≈ 11%，墙钟读数可信**。

## 六、方法学沉淀（本轮新增）

1. **缓存机制本身也是「结构」**：`Map` vs 定长直接映射表差 **12.9%**。
   查表次数到千万级时，**「用什么结构查」比「查几次」更重要**。
2. **flat 表要显式处理「换 key 域」**：原 WeakMap 天然隔离不同 `geo`；
   换成全局定长表后必须**在 geo 变化时整表失效**，否则会跨场比赛命中（错误结果）。
3. **1 项记忆 vs 定长表**：相邻命中才有效（T6 失败）；跨步重复要用表（T7 成功）。
4. **同一次测量里 CPU 口径与墙钟口径可以差 4 倍**（3.4% vs 12.9%）⇒
   一律以墙钟为准，并**用累计测量交叉验证**单项结论。
