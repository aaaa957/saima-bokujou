## 二、方法教训（本轮最重要）：测量工具的三处伪影

**结论先行：一个会系统性说谎的跑分工具，比没有工具更糟 —— 它会让你按错误方向优化一整轮。**

### 伪影 ①：同一进程内连续加载多个引擎副本 → 随位置单调变慢

原先的对比脚本写法是「在一个 node 进程里先 `require` 基线、跑一场；再 `require` 改后、跑一场」。
实测得到的 CPU **只取决于副本在列表中的位置**：

```
0.974× 0.886× 0.939× ...        ← 位置 1..5，越靠后越慢
1.14s  1.50s  1.67s  1.86s 1.67s 1.73s 1.84s 1.94s   ← 8 个变体，几乎单调递增
```

这不是代码差异，是同进程的 **JIT 状态与堆相互污染**。
**修法**：每个引擎副本、每个场次各起一个**独立子进程**。

### 伪影 ②：测量窗口太短 → 测到的是 JIT 预热方差

即使改成独立进程，若只跑 300 步（≈1.7 s CPU），同一变体在两次运行里可以差 **±20%**：
`p1b` 曾读到 `0.693×`，也曾读到 `1.123×`。
**修法**：先跑 `warmup` 步把 JIT 跑热，再强制 `global.gc()`，然后才测量；测量窗口放长到 1200–2000 步。

### 伪影 ③：run-to-run 漂移（残余）

即便按 ①② 修正，仍有 **~6% 的系统漂移**（同一份 `base` 在同一轮里首位 4.14 s、末位 3.91 s）。
**修法**：**A/B 交替**（A,B,A,B,A,B）取配对比值，而不是"跑一遍 A、跑一遍 B"。

修正后 `base` 的重复性达到 **1.3%**（11.08 / 10.94），工具才真正可用。

### ⚠️ 由此产生的一个推论（关于第一轮）

第一轮的「移除 `trafficProgressCache`」是**用同进程脚本**验证的 —— 它同样吃了伪影 ①。
不过伪影 ① 是**惩罚后测者**，而那一轮"改后"是在后测的位置上还快 1.42–1.60×，
**说明那个收益是真实的（且被低估）**。第一轮的结论方向可信，量值偏保守。

## 四、真实赛场的调用结构（插桩实测）

场景：12 匹 @ 京都芝外A 2400 m / 300 步。工具：`tests/perf-instrument-v11.py` + `tests/perf-counters-v11.js`。

| 量 | 数值 | 含义 |
|---|---:|---|
| `laneAdvance` 调用 | 1,170,680 | **每步 3902 次**（12 匹马 ⇒ 每马每步 325 次逆投影） |
| `routeArcState` 调用 | 5,188,791 | 每次 `laneAdvance` **4.4 次** |
| `routeArcState` 缓存命中率 | **51.44%** | 命中来自 `origin=stateAt(H.s)` 在同一决策内的重复 |
| `referenceArcAt` 调用 | 2,519,921 | = 未命中次数 |
| `referenceArcAt` 平均二分比较 | **11.92 次** | 表长 3793 |
| `routeTablePoint` 调用 | 10,439,909 | **每步 34,800 次** |
| `raceKinematicProposal` 调用 | 566,538 | ≈ 每次 `projectionMove` 的 `propose` 次数 |

**调用链**：`laneAdvance` → `distanceTo` → `routeArcState` → `referenceArcAt`

即：**`routeTablePoint` 的 1040 万次调用，几乎全部由 `routeArcState` 未命中经
`referenceArcAt` 的 5 点求积触发。**

## 五、方向 1（`budgetSpeed` / `finishPlan`）：为什么逐位等价下「少跑几次」不可能

inclusive 时间分解（真实赛场）：

| 函数 | inclusive | 主要来源 |
|---|---:|---|
| `step` | 87.7% | — |
| `projectActions` | **81.4%** | 48.6% ← `finishPlan`；32.8% ← 候选动作投影 |
| `run`（投影主循环） | 77.7% | 77.7% ← `projectActions` |
| **`finishPlan`** | **48.7%** | **38.7% ← `budgetSpeed`** |
| **`budgetSpeed`** | **38.8%** | 100% ← `runAI` |

`budgetSpeed` 的形式是：

```js
let low=3,high=H.maxV;
for(let i=0;i<9;i++){                          // ← 9 次「跑到终点」的全场投影
  const mid=(low+high)/2;
  if(finishPlan(H,mid,draftDistance,{reserve,earlyExit:true}).feasible) low=mid;else high=mid;
}
return low;
```

**返回值只有 `low`，而 `low` 由这 9 次 `feasible` 的取值序列唯一决定。**
要在不改数值的前提下少跑，必须让被跳过的那几次的 `feasible` 取值**被证明**与仿真结果相同。
判据是**单调**的，所以「用更紧的初始区间省迭代」会改变 9 个二分中点 ⇒ **数值必变**。

⇒ **可行性只剩两条**：

1. **让每一次投影更便宜** —— 即方向 2/3 所做的事（本节其余部分的实测：这条路走不通，见 §六/§七）。
2. **引入「可证明的界」提前判定** —— 代码里已有同类范式（`geo.progressCoefUpperBound`、
   `trafficRouteIntervalBounds`、`certificates`）。若能对某个 `mid` 用一个**保守的能量下界**
   证明「必然不可行」而不必仿真，且该界**永不误判**，则被替代的那次 `feasible` 取值与原仿真相同
   ⇒ 逐位等价。**这是一个研究课题，本轮未实施。**

另外注意：`earlyExit` 已在起作用（`projectActions` 里 `peakPowerShortfall>1e-7 ||
ledger.requiredDraw > initialReserve+ledger.recovered+1e-7` 时 break），所以第 2 条路的收益
上限是「比 earlyExit 更早地证明不可行」所省下的那部分。

## 六、两处反直觉的否证（可避免重复踩坑）

### ① 放大 `routeArcState` 缓存上限 —— 命中率涨、CPU 反而涨 47%

`routeArcState` 的缓存上限写死在 4096，而每步产生 8400 次未命中（**每步清空两次**）。
直觉上把上限放大应能显著提高命中率。实测：

| CAP | 命中率 | `routeTablePoint` | CPU（含计数器开销，只看趋势） |
|---:|---:|---:|---:|
| **4096（现值）** | 51.44% | 10,439,909 | **1.984** |
| 16384 | 53.06% | 10,041,735 | 2.047 |
| 65536 | 53.68% | 9,925,965 | 2.750 |
| 262144 | 54.67% | 9,804,846 | 2.953 |
| 1048576 | **59.65%** | **8,827,042** | 2.906 |

**命中率 +8.2 pp、`routeTablePoint` −15.5%，但 CPU 反而 +46%。**
原因：大 `Map` 的查找本身是**内存带宽/缓存未命中**瓶颈，且作为 GC 根使回收变贵。
⇒ **4096 这个上限选得很好，不要动。**
⇒ 也解释了为什么本轮所有「减少算术/分配」的改动都无效：**瓶颈是内存访问，不是算术。**

### ② `projectionBodySweep` 先判横向早退 —— 逻辑更省，实测更慢

`projectionBodySweep` 被 O(n²) 的同伴碰撞检查调用，而横向余量 `(wid_H+wid_F)/2+0.10`
**不依赖路线几何**；原式却先算纵向（要查两次路线）再与横向相与。
改成「先判横向、不重叠就早退」**逻辑上严格更省且逐位等价**，但实测：

| 比较 | 结果 |
|---|---|
| `D3` → `D3 + D3_SWEEP` | 0.926× → **1.081×**（慢 16.7%） |
| `c1` → `c1 + D3_SWEEP` | 0.906× → **1.020×**（慢 12.6%） |

⇒ **已否证、丢弃。**（V8 行为，非逻辑问题。）

### ③ 顺带否证：`routeStationLowerIndex` 的「最近一次」记忆

它每次调用都做一次 WeakMap 查询（实测 1040 万次）。加一级记忆后实测 **0.989×**（中性）。
⇒ 收益不显著，不值得引入。

## 七、非加性交互（方法论上的重要发现）

同一批改动，单独测与组合测的结论**会翻转**：

| 变体 | 第 1 次测量 | 第 2 次测量 |
|---|---:|---:|
| `p1b`（`routeTablePoint` 去闭包+去对象） | 0.693×（更快） | **1.141×（更慢）** |
| `c1`（= p1b+p2+p3+d3） | **0.906×** | **1.042×** |
| `propose`（`proposalCache` 按需建表） | 0.887× | 1.189× |

⇒ **这类微优化在 V8 下不可推理**：源码的极小改动会改变内联预算，进而产生 ±10–20% 的
双向摆动。**结论：这类组合改动只能枚举实测，不能靠"每项都是严格更少的工作"来相加推理。**

## 九、下一轮的建议（按期望收益排序）

1. **减少 `laneAdvance` 的调用次数**（每马每步 325 次！）。
   来源已定位：`raceKinematicProposal` 566,538 次 ≈ `projectionMove` 里 `propose` 的调用数，
   而**候选动作评估路径有 28 + 28 次二分**（`demand=false` 时），`finishPlan` 路径只有 1 次。
   先插入计数器量清两条路径各自的 `propose` 次数与投影步数，再决定攻击哪个。
2. **给五点求积做「只要 metric」的专用路径**。`referenceArcIntegral` 只读 `.metric`，
   却调用了完整的 `routeTablePoint`（算 x/y/tx/ty/k 并建返回对象）1040 万次。
   这需要在**先做 §六① 的教训校验**之后再动手（去对象未必更快）。
3. **不要**再走「减少算术/分配」「放大缓存」这两条路 —— 已各自被实测否证。
4. 任何改动都必须：`tests/perf-ab-v11.js` 的**独立进程 + 预热 + 强制 GC + 交替配对**；
   `tests/traffic-coef-equivalence-v11.js` 的**逐位等价**（含真实赛场 6 场次）。
   两者都通过，才谈"更快"。**"逐位等价"是必要条件，不是充分条件。**
