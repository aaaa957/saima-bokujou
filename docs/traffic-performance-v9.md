# 交通求解性能与等价验证

本文件是开发源`44b09f`的历史检查，不代表最终生产版本。后续查出航向角衔接错误，旧试算不再用于正式验收。修复后重新完成的对照见[最终性能与等价验证](traffic-optimized-final-v9.md)。以下数据保留原哈希和原测试范围。

本次性能修改没有改变运动积分、供能、能量账或未来完整制动域。冻结源 SHA-256：`44b09fc4789ccacf6cf812251effc8f3367e9f4996aa7b597886bd83d85ab6f1`。

完整证据见 [traffic-performance-v9.json](traffic-performance-v9.json)。两个隔离源码压缩快照及 [测试程序](../tests/traffic-performance-v9.js) 可复验；快照仅供测试使用，游戏不会加载它们。

## 性能修改

1. `laneAdvance` 的单次逆解缓存固定起点的精确弧长、航向和初始系数；残差表达式、五点 Gauss 积分、Newton/二分顺序与停止阈值不变。
2. `followingSlack` 只在数学下界能够证明全时域安全时提前接受。无法证明时继续检查完整制动轨迹、几何断点和身体间距极小值。
3. 带反应余量的拒绝查询，一旦初态、终态或已检查的内部时刻出现明确负间距即可拒绝。部分负证只说明全域最小值不大于该值，不进入 pair cache；查询真实身体安全域时仍计算完整最小值或使用已证明的保守下界。
4. `routeArcState` 使用每个 geometry 独立、最多 4096 个精确数值键的缓存；不将路线位置取整。每个 tick 的 `propose(v, transverse)` 同样按精确输入复用提案对象。求解期间旧马状态不提交、提案字段不原地修改，因此复用不会改变结果。

## 全时域正证

以后一匹马的平行车道弧长表示两马间距：

`G(t) = G(0) + dFront(t) − dRear(t) + (tRear − tFront) × ΔheadingFront(t)`。

相同有限制动加速度 `a` 下，`dFront − dRear ≥ −max(0, (vRear² − vFront²)/(2a))`。Quintic Hermite 位置转换为 Bezier 后，用导数控制多边形支配参考路线的最大速度、最小速度和绝对曲率 `K`；不假设曲率恒定，也不依赖代码中对负曲率的截断。

只在前后两条车道都满足 `1 − |t − referenceLane| × K > 0` 时使用正证。前马的参考弧长不超过其物理停止距离除以上述正余量，因此绝对航向变化不超过 `K × 参考弧长上界`。减去最大相对停止距离和最大航向项，得到 `G(t)` 的保守下界。再除以 `maxReferenceMetric × (1 + maxLegalOffset × K)`，得到路线进度间距下界；扣除全域身体投影上界和反应余量后，仍为正才接受。

导数下界不可证、任何所需界非有限、任一车道余量不为正时，正证自动禁用。该路径不能使用离散采样上界代替数学包络。

## 等价验证

两阶段分别比较旧完整域版本 `18c9cf… → 2b711a…` 和中间优化版本 `2b711a… → 最终 44b09f…`。每阶段 6 个场景、11,865 个内部帧，每匹马每帧比较 `s/t/v/stamina/guts/retention/targetV/targetT`，最大误差均为 **0**。帧数完全一致。通过两个阶段的相等性，最终版本与旧完整域版本的实际轨迹和记账一致。

场景包含东京 1600 米 16/18 匹前 10 秒、东京 2000 米 16 匹前 10 秒、东京 2000 米 18 匹前 20 秒，以及此前出过交通故障的两场标准场地 1200 米完整比赛。两场完整比赛中，全部马的完赛时间、末 600 米、所有分段、最终指令和储备也完全相同。

`initialStage.sourceUnchanged=false` 描述当时磁盘源码后来增加缓存；比较使用的是开始时已经独立编译的不可变源码快照，不会读取后来修改的引擎。最终阶段 `sourceUnchanged=true`，完整标志与全部等价标志均为 true。

## 性能结果与限制

旧完整域版本与第一组优化的东京 2000 米 18 匹前 20 秒：wall 195.34 → 17.40 秒，帧 P95 438.40 → 29.86 ms。测试顺序执行，期间有其他测试并发，该时长不能直接当作通用加速倍率。

最后两项缓存的最终复测如下。CPU 秒为该 Node 进程消耗，wall 为实际经过时间；其他正式比赛试算同时运行，硬件负载会影响测量。

| 场景 | CPU 秒：中间→最终 | wall 秒：中间→最终 | 最终帧 P95 | 最终最大帧 |
|---|---:|---:|---:|---:|
| 东京 1600 / 16 匹 / 10 秒 | 1.953 → 1.859 | 2.097 → 1.876 | 9.69 ms | 179.50 ms |
| 东京 1600 / 18 匹 / 10 秒 | 1.968 → 1.423 | 2.052 → 1.456 | 7.38 ms | 141.99 ms |
| 东京 2000 / 16 匹 / 10 秒 | 2.078 → 2.266 | 2.741 → 2.302 | 16.32 ms | 258.84 ms |
| 东京 2000 / 18 匹 / 20 秒 | 38.937 → 31.859 | 48.136 → 37.337 | 57.53 ms | 798.58 ms |
| 标准 1200 / 16 匹 / 完整比赛 | 9.173 → 8.750 | 9.692 → 8.706 | 10.18 ms | 91.43 ms |
| 标准 1200 / 16 匹 / 同能力完整比赛 | 15.812 → 14.313 | 18.368 → 17.681 | 17.65 ms | 45.48 ms |

普通 16 匹场景已有改善，但密集 18 匹场景仍有显著峰值，**不能据此宣称已满足实时性能要求**。这些是计算和等价测试，不是浏览器渲染 FPS 测量。后续应先测单场游戏下的 CPU 热路径，再处理完整域求解成本、AI 预算时机或将计算搬到 Worker；保留完整身体安全域和确定性，不以减少安全检查来换帧率。

复验最后缓存阶段：`node tests/traffic-performance-v9.js`。复验旧完整域到中间优化阶段：`node tests/traffic-performance-v9.js --stage initial --out docs/traffic-performance-initial-probe.json`（较慢；不是新的现实拟合样本）。
