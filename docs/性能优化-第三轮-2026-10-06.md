# 性能优化 · 第三轮（2026-10-06）—— 找到成本规律；但测量精度不足以证实改动

> 本轮**没有合并任何引擎改动**。`lane` 与 `quad` 两处候选都在 1200 步窗口上显示过收益
> （−11.8% / −3~8%），但**都没能通过完整比赛与重复性检验**。
> 本轮真正的产出是：**一条可指导后续所有优化的成本规律**（解释了前两轮为何失败），
> 以及**一次比前两轮更深的测量方法修正**。

---

## 一、结论摘要

| 项 | 结论 |
|---|---|
| **成本规律** | 本代码库里「**多一层函数调用/闭包**」远贵于「分配一个小对象」—— 前两轮方向选错了 |
| 候选 `lane`（内联 `laneAdvance` 闭包） | 1200 步窗口曾 −11.8%，**完整比赛 ≈ +0.4%（中位数）**；复跑窗口符号翻转 ⇒ **不复现** |
| 候选 `quad`（展开五点求积） | 窗口三次 0.918/0.967/0.962（一致但弱）；**未通过完整比赛检验** |
| **测量新教训** | 同一场景 `base` 的绝对速度在**不同批次间漂移 >10%**（10.2s → 12.1s）⇒ **同一次运行内"首尾吻合"并不能证明该次运行有效** |
| **方向 1** | 彻底算清并封闭：96.3% 投影步来自 `finishPlan`、每步仅 1 次 `propose`、二分几乎从不执行；60.8% 的步是 `stamina<15%` 触发的 0.05s 刻意细步 |
| 新增否证 | `Math.hypot` → `sqrt(x²+y²)`：38%（[0,4]²）/ 33.6%（单位圆）逐位不同 |

## 二、本轮最重要的发现：调用层数 ≫ 对象分配

三轮的对照实验拼出一条清晰的规律。**全部为逐位等价改动：**

| 改动 | 层数变化 | 实测 |
|---|---|---|
| 引入 `routeSegment` + `routeHermiteMetric` 三层调用以**去掉返回对象** | **+3 层** | **慢 16.7%** |
| `routeTablePoint` 内层闭包提到模块作用域以**去掉 2 个内部对象**（第二轮 P1b） | 改用跨函数 scratch | **慢 14.1%** |
| 展开 `referenceArcIntegral` 的 `reduce` 闭包（**去 1 层回调 + 1 个捕获闭包**） | **−1 层** | 快 3~8%（窗口法，未证实） |
| 内联 `laneAdvance` 的 `distanceTo` 闭包（**去 1 个闭包 + ~4 次间接调用**） | **−1 层** | 窗口法曾测 −11.8%，**不复现** |

**解释**：年轻代的对象分配只是 bump 指针 + 立即回收，几乎免费；而多一层函数调用会消耗
V8 内联预算、需要参数打包、使值无法留在寄存器里。

**前两轮我一直在做「去分配」（去闭包、去对象、去 Map 分配），所以反复拿到负收益 —— 方向错了。**
这条规律的价值在于：**它把「该往哪优化」从猜测变成了可判断的准则**
（数一数热路径上的调用层数，而不是数分配次数）。

## 三、方向 1 的最终账：投影步都花在哪（已封闭）

**先纠正第二轮的一个猜测。** 我曾以为 `projectionMove` 的 28 次功率/跟驰二分是热点。
插桩结果**完全否证**（12 匹 京都芝外A / 300 步）：

| 计数器 | 值 | 含义 |
|---|---:|---|
| `projectionMove` 调用总数 | 566,538 | = 投影步数 |
| 其中 `demand=true`（`finishPlan`/`budgetSpeed`） | **545,709 = 96.3%** | 候选评估仅 3.7% |
| `propose` 调用（demand 路径） | 545,709 | **每投影步恰好 1 次** |
| **功率二分执行次数** | **0** | **从未执行** |
| 跟驰二分执行次数 | 226 | 可忽略 |
| 同伴马对（O(n²) 碰撞检查） | 1,145,595 | 全在 3.7% 的候选路径里 |

⇒ **二分不是瓶颈；瓶颈是「投影步数」本身**（545,709 步 = 实际比赛 4230 步的 **129 倍**）。

**这 54.6 万步的 dt 分布：**

| 项 | 数值 | 占比 |
|---|---:|---:|
| **细步（0.05s）** | **331,746** | **60.8%** |
| 粗步（0.5s） | 213,963 | 39.2% |
| 触发条件：**`stamina/staminaMax < 0.15`** | **304,188** | **55.7%** |
| 触发条件：`\|targetV − v\| > 0.8` | 68,055 | 12.5% |
| 触发条件：`v < 3` | 1,920 | 0.4% |

**结论**：60.8% 的投影步是**低体力阶段刻意使用的 0.05s 细步**，粗化即改变轨迹。
⇒ **方向 1 在「逐位等价」纪律下既不能减步数、也不能减二分次数**；
可行的只剩「让每一步更便宜」（即 §二 那条规律指的路）。

## 四、测量方法：本轮又发现一层更深的问题

第二轮的修正是「独立进程 + 预热 + 强制 GC + 交替配对」，当时 `base` 首尾吻合到 0.3~1.3%，
看起来可信。**本轮发现这还不够。**

### 现象：同一场景 `base` 的绝对速度在不同批次间漂移 >10%

12 匹 @2400m 京都芝外A，**同一个 `.perf/base.js`**，三次不同批次的 1200 步窗口：

| 批次 | base 实测 |
|---|---:|
| 筛查（第一轮） | 9.88 / 9.78 |
| 筛查（第二轮） | 10.36 / 10.09 |
| 筛查（第三轮） | 10.23 / 10.20 |
| 复跑（同「早段窗口」） | **11.453 / 12.078** |
| 复跑（赛中段窗口） | **11.171 / 11.796** |

**同一份代码从 9.78 漂到 12.078（±12%）。** 而同一次运行内的首尾却总能吻合到 0.3~1%。

⇒ **「同一次运行内首尾吻合」只证明该次运行内部稳定，不能排除整批次的系统性偏移。**
最可能的原因是外部负载造成的 **SMT 争用**（`process.cpuUsage()` 记的是 CPU 时间，
但被超线程共享物理核时会显著膨胀）。

### 后果：`lane` 的「−11.8%」不复现

| 实验 | 配对（A=base, B=lane） | 结论 |
|---|---|---|
| 筛查（早段窗口，1 对） | A 10.23/10.20 → B **9.03** | −11.8% |
| **早段窗口复跑（2 对）** | +4.6% / **−5.0%** | 符号翻转 ⇒ 噪声 |
| **赛中段窗口（2 对）** | +1.6% / **−6.9%** | 符号翻转 ⇒ 噪声 |
| **完整比赛（3 对）** | A 121.44/121.92/**96.80** vs B 121.92/122.84/121.64 | 中位数 **+0.4%** |

（完整比赛那一组里 base 出现 96.80 的**偏低 20% 异常值**，同样说明外部负载在干扰。）

⇒ **`lane` 的真实效果落在噪声地板以下；不能声称有效，故不合并。** `quad` 同理（未做完整比赛检验）。

### 修正后的测量规程（务必照做）

1. 独立进程（已是第二轮的做法）。
2. 预热 + 强制 GC（已是第二轮的做法）。
3. **必须交错成对**（A,B,A,B,…），**且配对数量 ≥6**，取**成对差的中位数**；
   不要依赖「单次运行内首尾吻合」。
4. **效果的判定门槛提到 ≥10%**：低于此值在本机（8 核、有外部负载）不可分辨。
5. 想分辨 5% 量级的效果，需要**专门的静默环境**或改用不依赖墙上时间的度量
   （本机目前没有可用的指令计数接口）。

## 五、另一处确认的否证

**`Math.hypot(a,b)` → `Math.sqrt(a*a+b*b)`：不可替换。**
V8 的 `hypot` 带防溢出缩放，末位常常不同：

| 采样域 | 逐位不同比例 | 首个反例（a, b, hypot, sqrt） |
|---|---:|---|
| [0,4]² 均匀 | **38.0%** | (1.9721…, 2.1643…, 2.9280844805145905, 2.92808448051459) |
| 单位圆上 | **33.6%** | (0.9999976904695719, −0.0021491988093200, 1.0000000000000002, 1) |

与第一轮的 `Math.pow(speed,6) → 连乘`（47% 不同）属同一类陷阱。

## 七、下一轮建议

**遵守 §四 的新规程**（这是能否得出结论的前提）：

1. **先修测量**：把配对数量提到 ≥6、取成对差中位数；并且**先在一对完全相同的副本上
   跑一遍**，确认该规程下"A vs A"的成对差中位数落在 ±2% 内 —— 否则任何结论都不可信。
2. **继续沿「减少调用层数」找**（§二 已 4 组对照验证）：
   最值得做的是**把五点求积的度量求值内联**。`referenceArcAt` 现在每个取点都调用一次
   `loopReferencePoint`/`routeTablePoint`，且各重新解析一次「取段」（5 次冗余索引查找）；
   而 5 个取点**必然落在同一节点区间内**（`q` 与 `q[lo]` 同区间，路线站点是节点网格的子集）
   ⇒ 取段只解析一次、度量可内联，可去掉 5 次调用 + 4 次索引解析。
3. **不要**再做：去对象 / 去分配 / 放大缓存 / 收紧二分 —— 各自已被实测否证。
