## 一、为什么先修测量器

第二、三轮连续两次「无可合并的引擎改动」，但真正的原因不是没有想法，而是**测不准**：

- 同一份 `.perf/base.js` 跨批次测得 **9.78 → 12.078s**（±12%）
- 同一改动的结论会**翻转符号**：`lane` 曾读 −11.8%，复跑 +4.6%/−5.0%；
  `quad` 0.918×↔0.967×；`p1b` 0.693×↔1.141×
- 于是判定门槛被迫提到 ≥10%，而候选改动都在 5% 量级 ⇒ **全部无法判定**

⇒ 本轮的结论是：**噪声的根因不是"机器忙"，而是「计时口径选错」+「槽位不对称」。**
修好后本底噪声 **2.0%**，判定门槛可降到 **~3%**。

## 二、根因诊断

### ①②③ 先排除了三个旧的假设

| 假设 | 实测 | 结论 |
|---|---|---|
| 电源方案导致降频 | 空闲时 CPU 性能 **145%**（睿频中）、负载 1%；持续 70s 单线程负载**越跑越快**（2M 次迭代 0.055→0.042s） | ❌ 无功耗墙 |
| Windows Defender 抢占 | 累计 CPU 710s（全机第一），但配对相邻测量已抵消慢漂移 | ⚠️ 存在但非主因 |
| 区块变慢 = 机器变慢 | 引擎自身每步成本随赛程 **20ms → 121ms（6×）**（后期 `stamina<15%` 走 0.05s 细步） | ❌ 是引擎真实成本曲线 |

块大小的实验也一并做了（当时用的还是 CPU 口径）：**块大小 10/25/50/100 步的离散度都在 17–21%**
⇒ 块大小不是变量。（该实验在加入墙钟口径之前，故其绝对值不具参考性。）

### ★ ④ 真正的根因：`process.cpuUsage()` 把 V8 后台线程算了进来

`process.cpuUsage()` 记的是**整个进程**的 CPU 时间 ⇒ 并发标记 GC、并发优化编译、
并行 scavenge 这些**后台线程**的消耗全部计入。它们**突发**且 A/B 之间**相关**，
无法靠配对抵消。三个直接证据：

| 证据 | 数据 |
|---|---|
| 同一装置、同一批数据，两种口径对比（4 次自检） | **CPU 口径散布 14.0%** vs **墙钟散布 2.0%** |
| 单次 `global.gc()` | **CPU 0.015s / 墙钟 0.004s** —— CPU > 墙钟，必有后台线程 |
| 墙钟/CPU 比值 | 纯计算 ≈ **0.89–1.51**；引擎块 50 步 ≈ **2.05 / 2.11 / 2.32**（被系统性抬高） |

块比值的范围也印证了这点：

| 口径 | 单块比值范围（6 轮示例） |
|---|---|
| CPU | [0.6000, 1.7806] —— 更大样本见过 **[0.2331, 3.5161]** |
| 墙钟 | **[0.8821, 1.0628]** |

**⇒ 此前"必须用 CPU 时间（避开被抢占的墙钟）"的判断是错的。**
墙钟只反映主线程推进，反而干净得多。

### ⑤ 槽位不对称与「换序配对」消解

即使都用墙钟，仍有「第一个加载的实例 vs 第二个加载的实例」的残余不对称。
设槽位偏差系数 `m`（对第二个加载者统一作用），两个引擎真实成本因子 `f_A`/`f_B`：

```
正常顺序（A 先加载）  r₁ = m · f_B / f_A
交换顺序（B 先加载）  r₂ = m · f_A / f_B
⇒ 效果 f_B/f_A = √(r₁/r₂)      ← m 被完全消掉
⇒ 偏差诊断 m = √(r₁·r₂)        ← 显著偏离 1 即证明槽位不对称存在
```

该推导对 `m` 的**成因**（JIT 后台编译、编译缓存、槽位缓存局部性…）不作假设，
只要它在两次运行之间稳定。

## 三、修法：最终测量规程

**单进程 + 每块 50 步乒乓交替（A,B / B,A 轮换）+ 预热 400 步 + 安定 3 轮 +
每块前 `global.gc()` + 墙钟口径 + 换序配对。**

细粒度交替的意义：成对测量要跨 18–34 秒，而环境噪声在**秒级**尺度上就在变
⇒ 一对之内 A 与 B 处在不同环境。切成 50 步的小块逐块交替后，
环境波动成为两者的**共模**。

```bash
# 自检（必须通过）
node --expose-gc tests/perf-ab-swap-v11.js .perf/base.js .perf/base.js \
     12 600 12 2400 京都芝外A 400 1
# 判定候选
node --expose-gc tests/perf-ab-swap-v11.js .perf/base.js .perf/cand.js \
     12 600 12 2400 京都芝外A 400 1
```

单次约 75s，远快于旧规程（1200 步独立进程）。

## 四、验证：自检 + 阳性对照

### 自检（A = B = base）

墙钟口径 4 次：`1.0077 / 1.0023 / 0.9881 / 0.9913` ⇒ **散布 2.0%，4/4 落在 [0.98, 1.02]**
同一 4 次的 CPU 口径：`1.0353 / 1.0689 / 0.9472 / 0.9293` ⇒ 散布 **14.0%**

换序自检（REPS=2）：

```
r₁（正常顺序）= 0.9865, 0.9992   中位数 0.9929
r₂（交换顺序）= 1.0045, 1.0057   中位数 1.0051
⭐ 效果 √(r₁/r₂) = 0.9939（−0.6%）      顺序内离散度 1.3% / 0.1%
   槽位偏差 m = 0.9990（≈1）
```

### 阳性对照（`.perf/pc_slow.js`）

把 `referenceArcIntegral` 的五点求积**算两遍**，第二遍结果丢进模块级变量防 DCE。
`pointAt` 是纯几何查询 ⇒ 第二遍结果与第一遍逐位相同 ⇒ **数值完全不变，只是更慢**。

```
r₁ = 1.3055   r₂ = 0.7597
⭐ 效果 = √(r₁/r₂) = 1.3109  ⇒ 测得「慢 31.1%」      ✅ 方向正确
   CPU 口径只读出 1.2191（慢 21.9%）—— 明显偏低，再次证明 CPU 口径不可用
   槽位偏差 m = 0.9959（≈1）
   两引擎摘要逐位相同 ✅
```

**结论：装置可用。** 本底噪声 <2%，能正确测出真实差异，且不引入方向偏差。

## 六、落地：采纳 `quad`（本轮唯一的引擎改动）

`referenceArcIntegral` 的五点求积由「每次调用新建捕获闭包 + `ARC_QUADRATURE.reduce(...)` 回调
+ 数组解构」改为**直线代码**，权重与节点在模块初始化时一次性解构：

```js
const [[Q_T0,Q_W0],[Q_T1,Q_W1],…,[Q_T4,Q_W4]]=ARC_QUADRATURE;
function referenceArcIntegral(pointAt,a,b) {
  if(b<=a) return 0;
  const d=b-a;
  let sum=0;
  sum+=Q_W0*(pointAt(a+d*Q_T0).metric??1);
  …（共 5 项）
  return d*sum;
}
```

**为什么逐位等价**：`reduce` 的初值是 0，累加序列为 `0 + w0·m0 + w1·m1 + …`；
新代码 `let sum=0; sum+=w0·m0; …` **保持完全相同的累加次序与结合方式**；
`d*sum` 与 `(b-a)*sum` 逐位相同（`d` 即 `b-a`）。

**为什么快**：`referenceArcIntegral` 在真实赛场每 300 步被调用 **252 万次**，
每次原先都要新建一个捕获闭包、再走 `reduce` 的回调与解构。
按第三轮确立的规律（**调用层数 ≫ 对象分配**），这里去掉的是**调用层**而非分配
—— 正是本轮唯一有效的方向。

**落地方式**：用变体生成脚本里的原串打补丁，保证与实测变体**逐字一致**
（`diff <(tr -d '\r' < sim.js) .perf/quad.js` = 0 行）。

### 逐位等价验证（6 场次，独立进程，vs `3890177`）

| 场次 | 改前摘要 | 改后摘要 | 等价 |
|---|---|---|---|

| 8匹 @2000m 抽象 | `47ee625089a36368` | 同 | ✅ |
| 12匹 @2400m 京都芝外A | `7ec79f7314e4b428` | 同 | ✅ |
| 8匹 @2400m 東京芝A | `6762f1eae78ec00e` | 同 | ✅ |
