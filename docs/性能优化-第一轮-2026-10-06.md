# 性能优化（第一轮）：用 profile 找「净亏损」而不是猜

日期：2026-10-06　分支：`experiment/system-consistency-v9`

## 一、为什么要做

两个直接的痛点：

1. **上线门槛**：线上 main 的观赛成本是 **0.043 CPU/赛事秒**（8 匹 2000m），
   而开发分支是 **0.470**（慢 10.9×）；16 匹 2400m 到 **0.773**，浏览器里会跨过实时线而**慢放**。
2. **迭代成本**：156 批次要跑 **3.0 小时**。批次慢的唯一原因就是引擎慢
   （3 小时 = 156 个任务 × 单场几十秒 CPU），所以**性能优化与批次提速是同一件事**。

## 二、方法

不猜热点，先 **CPU profile**（`--cpu-prof`，16 匹 2400m / 400 步，总采样 6501 ms）：

| 函数 | self |
|---|---:|
| `run`（投影主循环） | 14.61% |
| **`trafficProgressCoef`（车道系数缓存）** | **11.58%** |
| `projectionMove` | 8.13% |
| GC | 8.04% |
| `projectActions` | 7.40% |
| `powerCost` | 5.24% |
| `laneAdvance` | 4.29% |
| 路线几何（`kAt`/`abstractArcState`/`laneProgressCoef`/`elevationAt`） | ~7.7% |

**第一个嫌疑很扎眼**：缓存自己占 11.58%，而它要缓存的 `laneProgressCoef` 只占 1.94%。

## 三、① 移除 `trafficProgressCache`（已实施，逐位等价已验证）

**它是什么**：按 `(t, s)` 嵌套 Map 存储 `laneProgressCoef(s,t,geo)`，
且**每个物理步都 `new Map()` 重建**。

```js
function trafficProgressCoef(s,t) {
  let lane=trafficProgressCache.get(t);
  if(lane){const value=lane.get(s);if(value!==undefined)return value;}
  const value=laneProgressCoef(s,t,geo);
  if(trafficProgressCacheSize>=16384){trafficProgressCache.clear();...}
  ...
}
// tick() 开头：
trafficProgressCache=new Map(); trafficProgressCacheSize=0;
```

**A/B 实测**（`tests/traffic-coef-ab-v11.js`，16 匹 400 步，5 轮取最小）：

| 变体 | CPU | 全场摘要 |
|---|---:|---|
| 带缓存（原状） | 1.48 s | `a3db72e6…` |
| **去掉缓存** | **1.23 s** | `a3db72e6…` ✅ 逐位相同 |

**完整比赛验证**（`tests/traffic-coef-equivalence-v11.js`）：

| 场次 | 改前 CPU | 改后 CPU | 加速 | 等价 |
|---|---:|---:|---:|---|
| 8匹 @1200m | 5.45 s | 4.41 s | 1.237× | ✅ |
| 8匹 @2000m | 54.66 s | 34.16 s | **1.600×** | ✅ |
| 16匹 @2400m | 98.75 s | 75.78 s | 1.303× | ✅ |
| **合计** | 158.9 s | **114.3 s** | **1.389×** | ✅ |

⇒ **CPU/赛事秒：8 匹 0.470 → 0.289**（已达 ≤0.3 的目标）；**16 匹 0.773 → 0.519**。

### ⚠️ 这条纠正了我先前的一个判断

我在 2026-10-05 测过这个缓存的**命中率（80.9% / 91.7%）**，并据此判定它"必要，保留"。
**那个判断是错的。**

> **命中率高 ≠ 净收益为正。**
> 缓存自身的开销（嵌套 Map 两次查询 + 每个物理步重建整个 Map）超过它省下的计算。

这条已写进 `AGENTS.md` 的同源纪律里：**判断一个缓存该不该留，要看 profile 的净差，不是命中率。**

## 四、② `powerTerms` 的 `c2` 按马预计算（已实施）

```js
c2 = RACE_F.resistanceK · H.economy · ground(地面状态 × 力量) · H.surfaceCost
```

这四个输入在整场比赛中**都不被写入**（已 grep 确认：`surface`/`state` 是模块级量、
`H.economy` 与 `H.surfaceCost` 只在构造时设定、`adj` 全程只读），而 `powerTerms`
在每个投影步被多次调用（`powerCost` / `speedAtPower` / `motionPower`）。
原先**每次调用都要构造一个地面状态字面量并在其中查表**。⇒ 按马预计算到 `H.powerC2`。

## 五、③ ❌ 否证两处「看起来像优化」的改动

诚实记录两个**没有采纳**的方向——两者都会破坏逐位等价：

### 5.1 `Math.pow(speed,6)` → 连乘

实测 **2,000,000 个样本中 47% 逐位不同**（末位 1 ULP）：

```
Math.pow(16.08652261200797,6) = 17328981.680610146
x*x*x*x*x*x                   = 17328981.680610143
```

⇒ 会改变数值，**不做**。

### 5.2 `powerTerms` 复用同一个结果对象以减少 GC

看起来很干净（只有两个调用点、都是即用即弃），但实施后**立即报 TDZ 错误**：

```
ReferenceError: Cannot access 'POWER_TERMS' before initialization
  at powerTerms → speedAtPower → H.sustainableV → createRace (sim.js:1347)
```

原因：`powerCost` 定义在 `const POWER_TERMS` **之前**，而本函数体早期
（`createRace` 内的自检路径）就会调到 `powerTerms`。修复需要精确定位作用域，
而**该优化的收益并未验证** ⇒ **回退，不做**。

## 六、结论与下一步

| | 状态 |
|---|---|
| 8 匹场次 CPU/赛事秒 | **0.470 → 0.289** ✅ 已达 ≤0.3 目标 |
| 16 匹场次 CPU/赛事秒 | 0.773 → **0.519**（浏览器 ×1.6 ≈ 0.83，仍会掉帧） |
| 156 批次预计耗时 | 3.0 h → **约 2.2 h** |
| 全部改动 | **逐位等价**（三场完整比赛摘要一致） |

**还没做、但 profile 指明的方向**（下一轮）：

1. **路线几何查询（约 12%）** —— `laneAdvance` / `elevationAt` / `kAt` / `abstractArcState`。
   其中 `elevationAt` 对高程剖面做**线性扫描**，且 `local.s` 在投影内单调递增
   ⇒ 与当年 `routeCorners` 同类，可用游标替换（需处理 `mod lap` 的回绕）。
2. **`followingBodyClearance`（6.12%）** —— 也返回新对象（GC 源），
   但它有 8 处调用点，复用缓冲需逐一确认调用者不持有返回值。
3. **结构性：`budgetSpeed` 的 9 次二分 × `finishPlan`（每次都是一次"跑到终点"的完整投影）** ——
   这是"每次骑手决策约 24 次全程模拟"的根源。
   同时可验证：这 9 次调用**共用同一起点与同一条剩余路线**，其路线派生量本可共享。
   这是唯一可能带来**量级**收益的方向，但它触及预测与执行共用求解器的架构，
   需要单独设计与逐位验证。
