## 二、T8 · `routeArcState` 去对象分配（**采纳**：单测 2.9%，16 匹增量 **−9.3%**）

**结构性浪费**：`routeArcState` 每次**未命中**都分配一个 `{arc,angle}` 对象，而真实赛场
每 300 步未命中约 **252 万次** —— 这就是 GC 的第一大来源。

**做法**：记忆表改存两个 `Float64Array`（`RS_ARC`/`RS_ANGLE`），结果经两个模块级标量
（`RS_RET_ARC`/`RS_RET_ANGLE`）返回。调用方（`laneArcDistance`、`laneAdvance`）改为
**立即读走**这两个量（原先它们同时持有 2 个结果对象）。

**数值**：纯表示变更，逐位等价（6 场景全绿）。

**实测**：

```
单测（换序配对，12 匹）：r₁ = 0.9410   r₂ = 0.9988   m = 0.9695
   ⭐ 效果 √(r₁/r₂) = 0.9706 ⇒ 快 2.9%
16 匹 min-of-5 墙钟（A=T11，B=T11+T8）：最小 5.292 → 4.801
   ⭐ **−9.3%，4/4 轮同向** ← 这才是它的真实增量
```

**旁证**：profile 里 **GC 15.09% → 5.45%**（⚠️ 份额本身不可靠，见 §六）；
**真正硬的证据是插桩直测**：`routeArcState` 每 300 步未命中 **2,687,178 次**（命中率 48.21%），
也就是消掉约 **269 万次对象分配（≈100 MB）**。

## 三、T9 · `loopMetricK` 定长表记忆化（**否证**，快 0.7%）

**动机**：`loopMetricK` 是 profile 的 #1 self（13.06%），每 300 步被调用 **420 万次**，
且同一个 `q` 常被反复求值（`powerTerms` 对同一个 `at` 先问曲率再问进度系数）。
**插桩实测命中率 76.32%**（高于 `routeArcState` 的 51%）。

**结果**：`r₁=0.9990`、`r₂=1.0136`、`m=1.0063`（很干净）⇒ **效果 0.9928（快 0.7%）**。
累计判定（A=第六轮末，B=+T8+T9，REPS=2）得 **0.9632（快 3.7%）**，与 T8 单独 2.9% + T9 单独 0.7%
完全吻合 ⇒ **T9 确实只有 0.7%**。

⇒ **低于 3% 门槛，按纪律回退。** 这是一个重要信号：**给纯计算加记忆化 ≈ 无效**
（与第六轮 T7「Map → 定长表」快 12.9% 形成对照 —— T7 的收益来自**消掉 Map 的开销**，
不是来自提高命中率）。

## 四、T11 · `powerTerms` 一次求出曲率与进度系数（**采纳**：单测 2.3%，16 匹 **−3.9%**）

**结构性浪费**（`powerTerms` 内部）：

```js
const curvature = laneCurvatureAt(at,transverse,geo), ...   // → kAt → loopMetricK
  gravity: 9.81*gradientAt(at,geo,g) * laneProgressCoef(at,transverse,geo)   // → loopMetricK（同一个 q！）
```

两条调用链、**同一个 `at` 被求值两次**。

**做法**：在 `powerTerms` 里调 **一次** `loopMetricK`，据此同时构造曲率与进度系数。
表达式与两个原函数**逐字一致**；`chute` 与抽象场地分支**一律回落到原函数**，行为不变。

**数值**：逐位等价（6 场景全绿）。

**实测**：单测 `r₁=0.9931`、`r₂=1.0398`、`m=1.0162` ⇒ 效果 0.9773（快 2.3%）；
16 匹 min-of-5 墙钟（A=第六轮末，B=T11）：最小 **5.361 → 5.153（−3.9%）**，4/4 轮同向。

## 六、本轮累计 —— **换序配对在噪声地板上给出了错误方向，靠「交替 + min-of-N」定案**

```
A = 第六轮末（f495f2c25defe842）   B = 本轮末（T8 + T11）
```

| 装置 | 被测对象 | 结果 |
|---|---|---|
| 换序配对（12 匹，REPS=2，墙钟） | T11 | `1.0060`（**慢 0.6%**） |
| 换序配对（16 匹，REPS=1，墙钟） | T11 | `1.0117`（**慢 1.2%**） |
| 交替 4 轮 × **min-3（CPU 口径）** | T11 | **4/4 轮 B 更快** |
| 交替 4 轮 × **min-5 墙钟**，12 匹 | T11 | 4/4 轮 B 更快，最小 3.587 → 3.575 |
| 交替 4 轮 × **min-5 墙钟**，**16 匹** | T11 | **4/4 轮 B 更快**，最小 **5.361 → 5.153（−3.9%）** |
| 交替 4 轮 × **min-5 墙钟**，**16 匹** | **T8 的增量**（A=T11） | **4/4 轮 B 更快**，最小 **5.292 → 4.801（−9.3%）** |
| **交替 4 轮 × min-5 墙钟，16 匹** | **本轮累计** | **4/4 轮 B 更快，最小 5.453 → 4.744（−13.0%）** |

**判读（这是本轮最重要的方法论发现）**：

- **换序配对给出反向结论（慢 0.6~1.2%），而它错了。**
  原因：它的单次窗口是 `12×50 步`，本底噪声（顺序内离散度 **4.7% / 4.9%**）与要测的效果同量级
  ⇒ **在噪声地板上，换序配对会有一半概率给出错误方向。**
- **交替 + min-of-N 把每轮装置噪声压到很低**：跨 12/16 匹两个规模、三种对比 **12/12 轮同向**，
  最小值的相对差稳定在 4–13%。**min 对争用最鲁棒**（取最小 ≈ 取"最接近未被争用"的那次）。
- **口径**：CPU 口径方向正确但**高估**（含 V8 后台线程的 GC/编译 CPU）⇒ **判定一律以墙钟为准**。
- **别拿 profile 的 GC 份额当证据**（第七轮 profile 给 `15.09% → 5.45%`，与实际不符）。
- ⚠️ **也别用「数 GC 事件」当捷径**：当时比的是 `base_t8.js`（第六轮末）与 `t11.js`
  （= 第六轮末 + T11），**两者都还没有 T8**（T11 是从回退后的工作树生成的）
  ⇒ 那次 `363` vs `364` 什么都没证明。**教训：先确认变体文件里真的含被测改动。**
- ✅ **T8 的机制用插桩直接量（有效证据）**：`routeArcState` 在 12 匹 2400m / 300 步内
  被调用 **5,188,791 次**、命中率 **48.21%** ⇒ **未命中 2,687,178 次（每投影步 4.92 次）**
  ⇒ **T8 确实消掉了约 269 万次对象分配/300 步（≈100 MB）**。机制成立。

**处置**：采纳 **T8 + T11**，**本轮 16 匹 −13.0%**（4/4 轮同向，min-of-5 墙钟口径）。

**官方 6 场次全程等价**（`tests/traffic-coef-equivalence-v11.js 34c0f0e`，21 分 36 秒）：
`e798e8a1a7059cad` / `47ee625089a36368` / `7ec79f7314e4b428` / `6762f1eae78ec00e` /
`c8859363869e8359` / `d3508e0af2552a4b` —— **6/6 逐位相同** ✅（含完整比赛）。
⚠️ 该脚本的「加速」列给 **0.915×（改后更慢）**，与交替 min-of-5 的 **−13.0%** 矛盾 ⇒ **不可采信**：
它是 **CPU 口径 + 顺序执行（改后总在后）**，正是第二轮记录过的两个伪影。

**端到端旁证**：最终引擎跑 **16 匹 @2400m 京都芝外A 完整比赛**，摘要 `4ece4e1d931d718e`
**与第六轮末逐位相同** ✅；绝对数值 CPU `148.656s` / RACE_T `145.483` = **1.022 CPU/赛事秒**
（单次测量、本机有争用 ⇒ 与第六轮 1.006 的差别属噪声，**不可作为变慢的证据**）。

## 七、结论：逐位等价的地板已经到了

把五～七轮的「单处改动收益」排在一起看：

| 轮次 | 最好的单处 | 本轮各处 | 轮合计 |
|---|---|---|---|
| 第五轮 | **−20.4%**（S1 求积就地内联） | −3.7%（T2）/ −0.9%（T1） | **−21.5%** |
| 第六轮 | **−12.9%**（T7 Map→定长表） | −3.2%（T5）/ 否证 T6 | **−36.0%**（vs 第五轮前，16 匹） |
| **第七轮** | **−9.3%**（T8 去对象分配，16 匹增量） | −3.9%（T11）/ 否证 T9、T12 | **−13.0%**（16 匹） |

⇒ **收益已从两位数掉到个位数，而且出现了"负收益"候选。**
剩下的大头都**没有可消掉的结构浪费**了：

- 内在数学：`loopMetricK` + `arcCellIntegral`（Hermite + `Math.hypot`，约 15%）
  —— `Math.hypot` 不能用 `sqrt` 替代（实测 38% 逐位不同）
- 投影机制：`run` + `projectionMove` + `projectActions`（约 21%）
  —— 545,709 个投影步（= 实际比赛 4,230 步的 **129 倍**），96.3% 来自 `finishPlan`/`budgetSpeed`
- GC 5.45%（已从 15% 压下来）

## 八、156 批量的估算（用户提问）

**已知**：156 批次 = 墙钟 **10840s ≈ 3.0h**，156 任务 ⇒ **69.5s/任务**；
而 17 匹真实赛场单场 CPU 在 200s 以上 ⇒ 批次是**多路并行**（约 3–4 路）
⇒ **CPU 降 X% ≈ 墙钟降 X%**（并行效率不变时）。

**换算**：

| 阶段 | 相对量（同会话换序配对） | 156 批量（墙钟） |
|---|---|---|
| 第五轮前（quad） | 1.000 | 3.0h |
| 第六轮后 | **−36.0%**（16 匹） | **约 1.92h** |
| **本轮后** | **−13.0%**（16 匹 min-of-5 墙钟） | **约 1.65h** |

⇒ **不会再"动不动 3 小时"**：现在是 **约 1.65h**（−45% 左右）。
⚠️ 这是按 CPU 降幅换算的估算；真机批次实测会受 **SMT 争用**影响，别用单次批次耗时下结论。
（若批次完全 CPU 饱和，本轮那 ~3% 的 CPU 下降也会体现为墙钟下降。）

## 九、性能「差不多了」的标准（建议）

**唯一硬标准**：**浏览器里最坏场次（18 匹 / 3200m）1x 播放不慢放**。

换算成可测的量：模拟 1 秒赛程的墙钟须 ≤ 1 秒，且要给渲染留余量 ⇒
**CPU/赛事秒 ≤ 约 0.35**（3× 余量）。

**现状**：16 匹 @2400m = **1.006 CPU/赛事秒**（第六轮末实测，且当时机器有争用、可能偏高）。

⇒ 距离档 2 还差约 **2.7×**；逐位等价五～七轮已累计拿下 **约 −60%**（1.696 → 约 0.68 的推算值），
但剩下的都是内在数学与投影机制 ⇒ **到不了 0.35**。

**要达标只有两条路**：

| | 做法 | 代价 |
|---|---|---|
| **A** | 把模拟移出播放路径：Web Worker + **整场预计算 + 回放** | **不改数值**；但开赛前要等（16 匹约 40s） |
| **B** | **减少投影工作量**（投影步 = 实际步的 129 倍） | **改数值**，必须重做数值验收 |

**建议**：性能先收在这里，回比赛系统；档 2 留到**合并 main 之前**再处理
（理由：数值验收本身还没过——冠军时间 `reserved2020` 分区 |rel| 5.2% > 5% 门槛——
两个改动叠在一起会互相干扰、难归因）。
