## 二、S1：五点求积就地内联 —— **快 20.4%**

### 结构性浪费

真实赛场每 300 步，`referenceArcAt` 里的五点求积要**取样 1260 万次**，
每次取样都走完整的 `routeTablePoint`，而它每次调用要：

1. 新建一个捕获闭包 `component`
2. 新建 x/y 两个 `{p,v,a}` 对象 + 1 个返回对象
3. `routeStationLowerIndex` 搜索站点区间

—— 却只为了读一个 `.metric`。这正是当时 profile 里
`routeTablePoint` self 15.98%、GC ≈15%、`routeStationLowerIndex` 4.59% 的主要来源。

### 关键结构事实（已验证）

**表节点数组 `q` 与站点数组 `loop.stations` 逐元素完全相同**
（京都芝外A 3793、東京芝A 4171、中山芝外A 3684，逐元素比对全等）；
引入线表节点也与采样网格相同（985 = samples 数）。

⇒ 五点取样必然落在**同一个**表区间 `[q[i], q[i+1]]` 内
⇒ 区段索引就是 `i`，无需再搜索；也不需要 `pointAt` 的返回对象。

### 实现

新增 `arcCellIntegral(table,i,q)`，把区段解析与 Hermite 求值全部就地展开：

- 与 `f` 无关的量（`p/v/acc` 与 `D/E/F`）提出循环、**只算一次**
  （原实现每个取样点重算一遍）
- 直线段保持原语义：`loopReferencePoint` 对该段返回的对象**没有 `metric` 字段**，
  原式 `??1` 使测度恒为 1（`home`/入弯/出弯都是站点，故区间不会跨界，用区间端点判定即可）
- 网格表（引入线）保留逐点解析，写法与 `routeTablePoint` 的 `else` 分支完全一致
- **逐位等价保证**：取样位置、Hermite 表达式、乘法与累加次序全部原样保留

### 实测

```
r₁ = 0.8047（A 先加载）   r₂ = 1.2699（B 先加载）   m = 1.0109
⭐ 效果 √(r₁/r₂) = 0.7960 ⇒ 快 20.4%
```

## 三、T1：`referenceArcAt` 的二分 → 米级「种子桶」—— 快 0.9%

`referenceArcAt` 每 300 步被调 252 万次，每次二分 **11.92 轮**（≈3000 万次比较）。

改为与 `routeStationLowerIndex` **完全相同**的手法：米级 `Uint32Array` 只给出搜索起点，
精确区间仍由同一套 `<=` 比较定位 ⇒ 不改变任何浮点结果。

实测 **快 0.9%**（两个顺序方向一致）。低于 3% 门槛，但属**严格更少工作**，故保留。
**附带信息**：这条只有 0.9% 说明「二分搜索」并不是 `routeArcState` 那 18.69% 的来源。

## 四、T2：赛道测度/曲率就地内联 —— 快 3.7%

profile 显示：`laneProgressCoef` inclusive **11.05%**（其中 8.36% 经 `routeReferencePoint`）、
`kAt` 经 `routeReferencePoint` **3.04%** —— 合计 11.4% 只为读 **`metric`** 与 **`k`**。

而原路径是 4 层调用 + 4 次对象分配：

```
laneProgressCoef → routeReferencePoint → loopReferencePoint → routeTablePoint(建 4 个对象)
```

新增 `loopMetricK(q,loop)` 就地求 `(metric,k)`（结果经两个模块级量返回）：

- 区间解析、Hermite 表达式、运算次序与 `routeTablePoint` 完全一致 ⇒ 逐位等价
- 直线段沿用原语义（原对象无 `metric` 字段，`??1` 使测度恒为 1、曲率 0）
- 引入线 / 负弧长分支仍走原 `routeReferencePoint`，行为不变

实测 **快 3.7%**（槽位偏差 m=0.9634 偏大 ⇒ 保守取 2–4%；属严格更少工作，保留）。

## 九、方法学沉淀（本轮新增）

1. **先问「谁为了一个字段付出整条调用链」**——比问「谁热点高」更能找到结构性机会。
2. **就地内联的前提是「结构事实」**，必须先证明（例如「表节点 == 站点数组」是用
   逐元素比对证出来的），否则内联会改变数值。
3. **无副作用地复用本项目既有手法**：`routeStationLowerIndex` 的「种子桶」可直接搬给
   `referenceArcAt`，逐位等价且不引入新风险。
4. **每次改动都要复核**：本轮 4 个候选里有 1 个「首测 6.6%、复核 1.1%」。

## 十、附带完成 P0c：第一轮改动的真实赛场收益 = **约 2%**（不是 1.32×）

第一轮文档写「156 批次 3.0h → **约 2.2h**」，但那三个实测场次用的是**抽象场地**，
而批次跑的是真实赛场（路线几何 42% vs 抽象 12%）——第二轮已指出该数字不可外推，
但当时测不准（±14% 噪声），无法给出答案。**本轮装置修好后可以直接判。**

```
A = 989e73a（第一轮前）    B = bfc9cbc（第一轮后）
17 匹 @2400m 京都芝外A，12 轮 × 600 步
r₁ = 0.9851   r₂ = 1.0238   槽位偏差 m = 1.0043（≈1，非常干净）
⭐ 效果 √(r₁/r₂) = 0.9809 ⇒ **快 1.9%**
```

**结论**：
- 第一轮的「1.32×」几乎全部来自抽象场地；**真实赛场只值约 2%**。
- **符号为正** ⇒ 那两处改动**不需要回退**（此前担心它在真实赛场是负收益）。
- **「3.0h → 2.2h」应作废**：批次墙钟按约 2% 估算，即 **3.0h → 约 2.94h**。
  ⇒ 真正让批次变快的是本轮的 S1/T1/T2（−21.5%），而不是第一轮。

> 方法学：这正是「换序配对 + 墙钟口径」的价值——**它把「无法判定的猜测」变成了一个 5 分钟的确定答案**。
