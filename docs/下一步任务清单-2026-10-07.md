## P0c · 补测第一轮改动在**真实赛场**的实际收益（用户提问暴露的漏洞）

### 问题

第一轮文档写「156 批次预计 3.0h → **约 2.2h**」，但**那三个实测场次用的是抽象场地**
（`tests/traffic-coef-ab-v11.js` 第 58 行：`profile:'平坦'`；等价脚本当时同样如此，已在第二轮修好）。
而 **156 批次跑的是真实赛场**（各场真实 `course`/`dir`，中位 17 匹、11/30 场 18 匹）。

⇒ 抽象场地路线几何占 **12%**，真实赛场占 **42%** —— **成本结构不同，该数字不可信。**

### 两处改动要分开评

| 改动 | 是否与几何相关 | 真实赛场预期 |
|---|---|---|
| `powerTerms` 的 `c2` 按马预计算 | **无关**（`resistanceK·economy·ground·surfaceCost`） | 同样受益（约 1% 量级） |
| **移除 `trafficProgressCache`** | **强相关（可疑）** | ⚠️ **可能反亏** |

**为什么「移除缓存」在真实赛场可疑**：该缓存包住的是 `laneProgressCoef(s,t,geo)`。
- 抽象场地：`laneProgressCoef` 走非 route 分支，**几乎免费** ⇒ 缓存省下的很少，而它自身开销（嵌套 Map + double 键，
  profile 实测 self **11.58%**）照样要付 ⇒ 删掉净赚（这是第一轮 1.20× 的来源）
- **真实赛场：`laneProgressCoef` 要调 `routeReferencePoint` → `routeTablePoint`（昂贵）**
  ⇒ 缓存省下的多得多，而自身开销一样 ⇒ **删掉可能净亏**

⇒ 第一轮的 1.32× 很可能**主要来自抽象场地**，真实赛场的收益未知，甚至**该改动本身可能是负的**。

- **正向且 >10%** ⇒ 保留，并按实测比例更新「批次能省多少」的估算
- **负向** ⇒ **回退该改动**，并更正 `docs/性能优化-第一轮-2026-10-06.md` 的结论
  （这也说明：第一轮「1.32×」是抽象场地结论，不该外推到批次）

### 附带：批次的耗时结构（用于把 CPU 降幅换算成墙钟）

## P0 · 修测量器（**这是当前唯一的阻塞点**）


### 为什么它是阻塞点

性能第一轮已拿到 **1.323×**（合计 170.8s → 129.1s，逐位等价，已提交 `bfc9cbc`/`3890177`）。
但第二、三轮空手而回，**不是因为没想法，而是这台机器测不准**：

- 同一份 `.perf/base.js`（12匹@2400 京都芝外A / 1200 步 / 预热400，3 轮取最小）
  在不同批次测得 **9.78 → 10.09 → 10.20 → 11.45 → 12.078 秒（±12%）**
- 而**同一次运行内首尾却总能吻合到 0.3~1%** ⇒ 现有规程只解决了「同进程内后测者更慢」的位置偏差，
  **没解决整批次的漂移**
- 后果：判定门槛被迫提到 **≥10%**；而候选改动都在 5% 量级 ⇒ 全部无法评判
  （`lane` 窗口法曾测 −11.8%，复跑变成 +4.6%/−5.0%，完整比赛中位数 +0.4%）

### 候选设计（**尚未验证**）

**单进程 + 交错成对 + 顺序交替 + 取比值中位数**

1. 同一进程内预热一次（跑够步数让 JIT 到稳态 + `global.gc()`）
2. 然后按 `A,B` / `B,A` / `A,B` / `B,A` … 交替测量（**下一对翻转顺序**）
3. 每对取**比值** `B/A` ⇒ 成对在时间上相邻，天然抵消整批漂移；顺序交替抵消位置偏差
4. **≥8 对**，取**比值中位数**
5. **自检门槛**：`A vs A`（两份完全相同的副本）的比值中位数必须落在 **[0.98, 1.02]**

建议新建 `tests/perf-ab-paired-v11.js`，接口：

```bash
# 用法：node tests/perf-ab-paired-v11.js <A文件> <B文件> <pairs> <steps> <horses> <length> <course> [warmup]
node tests/perf-ab-paired-v11.js .perf/base.js .perf/base.js 8 1200 12 2400 京都芝外A 400
#   ⇒ 自检：输出的比值中位数应落在 0.98~1.02
node tests/perf-ab-paired-v11.js .perf/base.js .perf/quad.js 8 1200 12 2400 京都芝外A 400
```

- 单进程内交替加载两个副本用 `delete require.cache` + 重新 `require`（**注意**：这正是第二轮发现的
  「同进程污染」的来源；本设计的要点是**两个副本相邻测量、且顺序交替**，使污染对称化。
  若自检失败，改用独立进程 + 同样 8 对交替。）

### 判定标准

- **通过**：`A vs A` 比值中位数 ∈ [0.98, 1.02] ⇒ 判定门槛可从 ≥10% 降到 **~3%**，继续 P0b
- **不通过**：本机不适合做 <15% 的性能判定 ⇒
  - 只做结构性改动（预期 >15%），跳到 P2b；
  - 或把基准脚本留到**机器空闲时**跑（关掉 Chrome / 代理 / 其他 node），并在自检通过后才采信

## P2a · bit-exact 结构改动（P0 通过后再做）

**方向已识别**：`referenceArcAt` 的 5 个求积取点**必然落在同一个节点区间内**
（`q` 与 `q[lo]` 同区间，且路线站点是节点网格的子集），因此可以：

1. **取段只解析一次**（现在每个取点各调用一次 `routeStationLowerIndex` ⇒ 5 次冗余索引查找）
2. **度量求值内联**（现在每个取点都调用一次 `loopReferencePoint`/`routeTablePoint`）

规模：`referenceArcAt` **252 万次 / 300 步** × 5 个取点 ⇒ 可去掉 5 次调用 + 4 次索引解析。

**依据的成本规律**（第三轮四组对照实验确立）：**调用层数 ≫ 对象分配**。
年轻代分配几乎免费；多一层调用才贵。

⚠️ **预警**：我做「去对象」的三次尝试全部变慢（+16.7% / +14.1%）——**不要**再走"去分配"。
要走"减调用层数"。

预期 **5–8%，不解决 16 匹还差 2× 的问题**。

## 附 B · 今天已避开的坑（**不要重复试**）

全部为逐位等价改动，全部实测无效或负收益：

| 已否证 | 结果 |
|---|---|
| **去对象 / 去分配**（去闭包、去内部对象、去 Map 分配、去中间数组） | 三次尝试 **+16.7% / +14.1%** 更慢；一次 −13% 净慢 ⇒ 方向本身是错的 |

| `Math.pow(speed,6)` → 连乘 | **47%** 样本逐位不同 |
| `Math.hypot(a,b)` → `sqrt(a*a+b*b)` | **[0,4]² 38.0% / 单位圆 33.6%** 逐位不同 |
| `projectionBodySweep` 先判横向早退（逻辑严格更省 + 等价） | **+12.6% / +16.7%** 更慢 |
| `routeStationLowerIndex` 加「最近一次」记忆 | 0.989× 中性，不值得引入 |
| 收紧 `budgetSpeed` 的二分区间 / 少跑几次 | **理论上不可能**：返回值 `low` 由 9 次 `feasible` 的取值序列唯一决定 |
| 尾段步长粗化（A1 老实验） | 会改数值；同源同种子下 8 匹慢 4×、16 匹快 2× |

**其它纪律**：
- 「逐位等价」是**必要条件不是充分条件**——`lane` 逐位等价全绿但更快不成立
- **组合不可加**：`quad`(0.918)+`traffic`(0.954) 合成 **1.035**；第二轮 5 处改动合成 1.131 ⇒ 只合并单项
- 性能改动的正确方向是「**减少调用层数**」：数热路径上的调用层数，不是数分配次数
