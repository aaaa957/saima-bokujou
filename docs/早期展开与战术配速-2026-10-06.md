## 一、要解决的问题

`docs/变道插空机制-2026-10-06.md` §八 已把病灶定在这里：14 匹马出闸后
**前 24 秒（1200 m 赛程的 36%）全场并排**，与内侧邻居的纵向间隔始终小于跟驰阈值
3.2 m ⇒ **任何变道都不合法** ⇒ 外侧闸位的马被锁在自己车道，把「平行曲线」的
几何惩罚（1200 m 达 4.5%、3200 m 达 6.6%）整额兑现成成绩差。

而 `tests/start-spread-diagnostic-v11.js` 证明这条路是可修的：
只要马群真的拉开（出发 10 s 纵向跨度 5.1 m → 14.8 m），
**闸位依赖、时间离散度、完赛密度、首末差四项同时改善**。

所以本轮要回答的是：**该用什么机制让马群在出闸后拉开？**

## 二、归因实验：5.1 m 的跨度由谁贡献

`tests/start-expansion-attribution-v11.js`（14 匹 / 1200 m / seed 20261005）
分别关掉「起步延迟差异」「配速意图」「加速度属性差异」：

| 变体 | spread4 | spread10 | 闸位ρ | 时间CV | within1 | **过 200 m 时间 SD** |
|---|---:|---:|---:|---:|---:|---:|
| base（现状） | 4.4 | **5.1** | 0.984 | 1.215% | 42.9% | 0.25 s |
| 起步延迟全同 | 2.1 | 2.6 | 0.993 | 1.318% | 35.7% | 0.13 s |
| 关配速意图 | 4.4 | **5.1（完全不变）** | 0.992 | 1.174% | 35.7% | 0.21 s |
| **延迟全同 + 关配速意图** | 2.3 | 2.8 | 0.972 | 1.282% | 35.7% | **0.00 s** |
| 出闸能力全同 | 3.6 | 4.3 | 0.993 | 1.187% | 42.9% | 0.18 s |
| 出闸能力+爆发力全同 | 3.6 | 4.0 | 0.988 | 1.323% | 50.0% | 0.13 s |

**三个可判定的事实**：

1. **起步延迟差异贡献了 spread10 的约一半**（5.1 → 2.6 m）。
2. **关掉配速意图对早期展开毫无影响**（5.1 → 5.1）——它改善的是赛后段结构，
   不是早期展开。
3. ⭐ **把这两项都关掉后，14 匹马到达 200 m 的时间完全一致（SD = 0.00）** ——
   即引擎里**除了这两项，没有任何早期分化机制**。加速度上限的差异
   （`出闸能力`、`爆发力`）**不产生可观测的差异**。

**根因（对 `startDelay` 的代码事实）**：

```js
startDelay: 0.12 + (100-adj['出闸能力'])*0.003 + rng()*0.15
//           常量        属性项（跨度≈0.06 s）      纯随机（跨度 0.15 s）
```

**随机项的跨度是属性项的 2.5 倍**——等于把"出闸质量"这个
**稳定的个体特征**做成了"每场重掷的随机噪声"。

## 三、两条候选路径的实测

`tests/start-expansion-sweep-v11.js`（14 匹 / 1200 m）：

| 变体 | spread10 | 闸位ρ | 时间CV | **within1** |
|---|---:|---:|---:|---:|
| 现状 | 5.1 | 0.984 | 1.215% | 42.9% |
| **A** 出闸反应个体化 K1=.010 K2=.05 | 4.0 | 0.988 | 1.293% | 35.7% |
| **A** K1=.020 K2=.03 | 4.8 | 0.988 | 1.239% | 35.7% |
| **A** K1=.035 K2=.02 | 9.2 | 0.971 | **1.350%（更差）** | 42.9% |
| **B** 起跑强度 span=.10 | 6.8 | 0.971 | 1.247% | **57.1%** |
| **B** span=.20 | 8.9 | **0.854** | **1.014%** | **57.1%** |
| **B** span=.35 | 13.2 | 0.891 | 0.872% | 57.1% |
| A2+B2 组合 | 9.9 | 0.968 | 1.283% | 57.1% |

**A 无效，B 有效。** 差别在机制性质：

- **A 只是把"位置"随机化**——它不改变"谁更快"，所以名次结构没改善：
  闸位 ρ 几乎不动（0.984→0.971），**时间离散反而变大**（1.215%→1.350%）。
  这正是"噪声"的特征。
- **B 让战术意图真正进入速度**——逃马真的抢前、追马真的留后，
  于是产生了**有意义的配速分化**：闸位 ρ 0.984→**0.854**、
  时间离散 1.215%→**1.014%**、within1 42.9%→**57.1%**（现实 58.9%）。

> **结论：拉开马群不能靠"随机化位置"，必须靠"让配速真的分化"。**

## 四、一个负结果：「物理起跑窗口」无效

引擎里存在一处**机制不一致**：

```js
// updateStartState（真正物理的定义）
// "起步完成取决于已达到的速度及仍需多少提速，不依赖走了多少米。"
H.startSettled = H.v>STALL_SPEED && H.v>=reference*0.95 && ...

// 但配速偏置的窗口却按【赛程比例】
const earlyWeight = clamp(1 - H.s/Math.max(1, length*0.35), 0, 1);   // 1200m→420m，3200m→1120m
```

同一个「起跑期」，一处按物理、一处按赛程比例。按文献（HIRAGA 1994：
起步后前 20 步完成加速，约 8 秒）它应当是**绝对时标**。
所以我试了物理版本 `earlyWeight = H.startSettled ? 0 : (1 - v/planned)`：

| 变体 | 1200m spread10 | 3200m spread10 | 1200m within1 |
|---|---:|---:|---:|
| base（比例窗口，span .05） | 5.1 | 11.1 | 42.9% |
| prop（比例窗口，span .20） | **8.9** | **16.0** | **57.1%** |
| **phys（物理窗口，span .20）** | **5.1（完全无效）** | 9.7（弱） | 35.7% |
| phys（物理窗口，span .15） | 5.1 | 9.7 | 28.6% |
| phys（物理窗口，span .25） | 5.1 | — | 35.7% |

**物理窗口在 1200 m 上完全无效，而且与 span 取值无关。**

### 原因（读代码得到，可复核）

```js
let a = clamp((desired-H.v)/response, -RACE_F.braking, Math.min(maxA, kineticBudget));
```

起步早期 `desired ≈ 20 m/s`、`v ≈ 0`、`response ≈ 1.12`
⇒ `(desired-v)/response ≈ 17.9 m/s²`，**远超 `maxA`**。
所以**加速阶段所有马一律顶在 `maxA` 上跑，请求速度完全不起作用**；
只有当 `v` 接近 `desired`、比例项降到 `maxA` 以下之后，请求速度才开始生效。

⇒ 物理窗口把偏置施加在"请求速度不生效"的区间，自然无效。

⭐ **这暴露了一个更深的缺口：引擎里「起跑强度」这条物理通道不存在。**
现实中骑手推马/拉缰直接作用于加速（M&A 2020 的核心结论就是
"起跑强度是最优策略的一部分"）；引擎里加速阶段的加速度是
`min(maxA, kineticBudget)`，与战术意图无关，也没有个体差异。
**列为下一轮候选（方法 2/3），本轮不动。**

## 五、选定方案与依据

**方案：把 `RACE_F.paceIntentSpan` 从 `0.05` 放大，让战术意图对配速的影响达到现实量级。**

形状仍然是涌现的，**没有硬编码**：

```js
frontBias  = clamp((plan.position-0.5)*2,-1,1)*0.6 + clamp((behavior.forwardness-0.5)*2,-1,1)*0.4
earlyWeight = clamp(1 - H.s/(length*0.35), 0, 1)
intentV    = clamp(planned * (1 + frontBias*RACE_F.paceIntentSpan*earlyWeight), 3, H.maxV)
```

- **谁抢前、抢多少**由每匹马自己的 `plan.position` 与 `behavior.forwardness` 决定；
- 偏置只作用于早段，中后段由"剩余储备"接管——前压者储备更低 ⇒
  `budgetSpeed` 复算出的配速自然回落，**拱形配速是结果而非写死的曲线**；
- 请求超功率上限时由 `projectionMove` 自身按 `maxPower` 二分下压，不产生不可行轨迹。

**现实依据（量级）**：逃马与追马的早期速度差约 **5–10%**（由配速图与
M&A 的"强起跑但强而不竭"推得）；本引擎 `frontBias` 的实际分布集中在 ±0.3 附近，
故 `span = 0.15–0.20` 对应约 5–6% 的速度分化——**与现实的量级一致，不是拍脑袋**。

⚠️ **性质说明**：这一步属于**方法 1（数值平衡）**，不是方法 3。
我做过的三步排查见 §六。

## 八、下一轮：把「起跑强度」这条物理通道补上（**已设计，未实施**）

§四 的负结果指出了一个比"调偏置"更根本的缺口。这里先把设计写下来。

### 8.1 缺口

```js
let a = clamp((desired-H.v)/response, -RACE_F.braking, Math.min(maxA, kineticBudget));
```

起步早期 `(desired-v)/response ≈ 17.9 m/s²`，**远超 `maxA`** ⇒ 实际加速度恒为 `maxA`。
也就是说：**马在起步时根本没有用满功率**，而 `maxA` 是全场统一的加速度上限附近的一个
近似常量（属性项被压缩到几乎不可观测）。

⇒ 现实里骑手**推马 / 拉缰**直接作用于起跑阶段的加速强度
（M&A 2020 的核心结论：起跑强度是最优策略的一部分；强起跑但强而不竭）；
引擎里**这条通道不存在**。

### 8.2 候选设计（**方法 3：补机制**）

让「用力强度」调节**加速度上限**，而不是调节请求速度：

```js
const effort = 1 + frontBias * RACE_F.launchEffort;      // 逃马更用力，追马更从容
let a = clamp((desired-H.v)/response, -RACE_F.braking,
              Math.min(maxA*effort, kineticBudget));      // ← 只放宽 maxA，不放宽能量
```

**为什么这样是对的**：

- **能量仍然守恒**——`kineticBudget` 不被放宽，所以"更用力"只会让马**更快撞上功率上限**，
  代价是**储备消耗更快**。这正是现实里的权衡：**用储备换早期位置**。
- **自然产生个体差异**——用力程度由每匹马自己的 `plan.position` / `forwardness` 决定，
  不是写死的数值。
- **它解决的正是 §四 那个负结果**：一旦 `maxA` 能被调节，加速阶段就有了自由度，
  "物理起跑窗口"（按速度进程施加偏置）才可能开始生效。

**必须验证的前置**：

1. **工程不变量**——`maxA` 是安全相关的参数（有限制动、跟驰余量都依赖它）。放宽它可能
   破坏 `finiteBraking` / `followingSlack`，**必须先跑 `--scope smoke` 才能继续**。
2. **不得让"更用力"突破能量账本**——`kineticBudget` 的约束必须保持，否则出现"免费加速"。
3. **参数 `launchEffort` 的取值要有现实依据**，不能拍脑袋：可从
   "逃马比追马早 200 m 快多少" 反推。

### 8.3 可行性已初步确认

| 量（1200 m 起步瞬间，属性≈80） | 值 |
|---|---:|
| `maxA` | ≈ **6.0 m/s²** |
| `kineticBudget = (maxPower − powerCost(v))/(massRatio·max(v,1))` | ≈ **123 m/s²** |

⇒ **`maxA` 是紧约束，马远未用满功率** —— 提高 `maxA` 确实会换来更大的功率消耗
（直到撞上 `kineticBudget`），即 §8.2 的权衡真实存在。

⚠️ **一处必须一起处理的实现细节**：`sim.js:1478` 存在 demand 分支

```js
const upperA = demand ? limits.maxA : Math.min(limits.maxA, limits.kineticBudget);
```

（`demand` 用于 `finishPlan` 的"最大能力"查询；真实物理步 2466 处**没有**这个分支。）
若只在物理步引入 `effort` 而不在预测侧同步，**预测与执行的加速度上限会不一致**，
违反本项目"预测与执行共用同一求解器"的架构要求。

### 8.4 优先级
